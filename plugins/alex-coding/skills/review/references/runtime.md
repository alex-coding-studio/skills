# PR-bound reviewer runtime

## Ownership and capabilities

`scripts/review_pr.py` creates one independent reviewer for one exact GitHub PR. It is an execution host: it invokes the selected CLI for relevant events and resumes that PR's exact session. It does not depend on Semina. Started with an author session, the same process is the PR's only runner: it also delivers author feedback and completes post-merge cleanup, see [Author delivery](#author-delivery).

Requires macOS/Linux Python 3.9+, Git, GitHub CLI with `gh_as admin`, repository read access for Git fetch, and an authenticated Codex, Claude or Antigravity (`agy`) CLI. Windows is unsupported because locks use `fcntl`. Required CLI flags are probed before launch. Unsupported execution is inactive review, not permission to substitute another runtime, account or service. When neither `--runtime`/`--review-runtime` nor `.ci/config.json` `review_runtime` is set, review defaults to `antigravity` with pinned model `gemini-4-hydrogen-high` (regardless of author runtime or complexity, while still honoring explicit `--model`/`--review-model` or `.ci/config.json` `review_model`); explicitly selecting `--runtime antigravity` (or `review_runtime: "antigravity"`) without a model still uses the default `claude` family. The runner passes the model and effort explicitly according to the policy below, independently of author settings, and never silently falls back.

## Model and effort policy

Select `--complexity` from the actual review risk and uncertainty, and give the reason in one sentence in the PR description. Defaults by kind of change: mechanical rewrites, documentation and copied configuration use `low`; ordinary behavior changes use `medium`; anything in the `high` row below uses `high`. Depart from the default only with a stated reason. Do not infer complexity from line/file counts or the author's preferred verdict.

| Complexity | Codex | Claude | Antigravity (`claude`, default) | Antigravity (`neon`) | Use |
| --- | --- | --- | --- | --- | --- |
| `deterministic` | `gpt-6-luna`, max | `claude-sonnet-5-5`, max | `claude-sonnet-5-5-high` | `gemini-4-neon-low` | Diagnosis verified, bounded behavior, known dependencies and meaningful coverage; no material security, persistence, migration, concurrency or interface uncertainty. |
| `low` | `gpt-6.2-sol`, low | `claude-opus-5-5`, low | `claude-opus-5-5-low` | `gemini-4-neon-low` | Straightforward review with a small amount of independent interpretation. |
| `medium` | `gpt-6.2-sol`, medium | `claude-opus-5-5`, medium | `claude-opus-5-5-medium` | `gemini-4-neon-medium` | Several interacting behaviors or boundary cases with understood scope. |
| `high` | `gpt-6.2-sol`, high | `claude-opus-5-5`, high | `claude-opus-5-5-high` | `gemini-4-neon-high` | Authentication/permissions/session safety, destructive persistence, migrations, concurrency, public interface changes or unclear impact. Also the fallback when unclassified. |

Regular models never exceed high. The deterministic tier's max is an explicitly accepted exception for the smaller Codex/Claude models. With `--runtime antigravity`, `--model` (or `delivery.py --review-model`, or `.ci/config.json` `review_model`) accepts a family alias (`claude` or `neon`) or an allowlisted exact `agy` model slug (`claude-opus-5-5-{low,medium,high}`, `claude-sonnet-5-5-{low,medium,high}`, `gemini-4-neon-{low,medium,high,xhigh}`, `gemini-4-hydrogen-{low,medium,high,xhigh}`). This selection does not waive independent review or any repository gate. A small authentication diff still selects high. Project-authorized mechanical review exemptions remain separate.

The selected complexity and model are stored per PR, included in checkpoints and returned by status; every exact-session resume uses them. Repeating `start` cannot silently change an existing choice. Review states and checkpoints created before model pinning keep their previous model selection (`gpt-5.6-sol` / `gpt-5.6-luna` or `claude-opus-5` / `claude-sonnet-5`) until explicit continuation, and Codex reviews already pinned to `gpt-6-sol` or `gpt-6.1-sol` keep their pinned model the same way; a fresh continuation selects the current model for its runtime and complexity (for Antigravity, preserving a pinned model when runtime/complexity/`--model` are unchanged, preserving its `claude`/`neon` family when only `--complexity` changes, and requiring explicit `--model` to change complexity on a non-family pinned slug). A newly discovered risk can require promotion: retain review progress and use the existing explicit continuation procedure rather than resetting rounds or switching an active session behind its owner. A continuation may supply `--complexity high`, `--runtime` and `--model`. Legacy checkpoints without a complexity choice use high. An unavailable model stops with retained evidence; it never triggers an automatic cheaper substitute.

Codex uses `codex exec` and `codex exec resume <exact-session>` with JSON output, a result schema and a read-only sandbox. Claude uses print mode, structured output and exact-session resume; built-in tools are restricted to Read, Glob and Grep, MCP servers are disabled and hooks are disabled for that invocation. Antigravity uses `agy` headless `stream-json` stdin/stdout with `--json-schema`, exact-session resume via `--conversation <conversation_id>`, a per-PR random-named custom read-only agent generated under `<state-directory>/.agents/agents/alex-coding-pr-reviewer-<id>.md` (`--agent`, `tools: [read_file, finish]`, verified not shadowed by `checkout`, removing write/edit/shell/subagent/swarm/workflow/schedule/web/question tools from the model's tool declarations), and defense-in-depth per-session `--settings` (`agentMode: ""`, `toolPermission: "request-review"`, `allowNonWorkspaceAccess: false`, `disableSlashCommands: true`, `permissions.deny: ["write_file(*)", "command(*)", "unsandboxed(*)", "read_url(*)", "execute_url(*)"]` plus each Semina write tool as `mcp(semina/semina_<tool>)`, and each Semina read tool allowed by exact name). Result collection fails closed unless the `init` event confirms both the generated `--agent` name and `permission_mode: "request-review"`. Remaining platform-injected declarations (`manage_task` and MCP wrappers) are either inert without command/schedule tools or limited to Semina read tools: an explicit deny returns a tool error and wins over any allow, while an MCP tool no rule names stops the headless run, so an unknown or new tool fails closed; `agy` has no `disableAllHooks` setting. The runner adds the PR state directory to the workspace with `--add-dir` and grants `permissions.allow: ["read_file(<absolute-state-directory>)"]`. This directory rule recursively covers `acceptance.md`, `current.patch`, `snapshot.json` and source files under `checkout/`. Headless request-review mode needs the explicit grant because it cannot prompt for read access. The worker process also receives `AGY_DART_DISABLE_READ_HOOK=1`, so a locally installed agy-dart read guard cannot block whole-file reads of the patch or sources above its size limit. In headless request-review mode a read outside the granted directory (for example a symlink into shared tooling) ends the turn without structured output; when the result reports `denied_actions` and no structured output, the worker resumes the same conversation up to twice, telling the reviewer not to retry the denied read and to finish from the evidence it has. Earlier event files are kept as `<token>.events.<n>.jsonl`. Workers inspect source/test assertions and reuse exact-revision execution evidence. They do not run write-requiring gates or make GitHub changes. The runner owns Git fetch, local state and authorized publication. These boundaries do not claim arbitrary third-party extensions provide an OS sandbox.

CLI contracts: [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive), [Claude programmatic execution](https://code.claude.com/docs/en/headless), [Antigravity headless mode](https://antigravity.google/docs/cli/headless). Verify installed capability and real session continuation when adapting another version; help output alone is not execution evidence.

## Launch after PR creation

The reviewer's default acceptance input is the PR description, refreshed from GitHub on every invocation. For evidence that cannot live there, pass a local `--acceptance-file`. The runner supplies a readable copy to the worker in its state directory as the acceptance input. Include the task card, its referenced decision cards or other readable local acceptance evidence there when using this option.

If the declared Semina provider is unavailable to the reviewer runtime, obtain the applicable scoped reads through authorized MCP access before startup and include them in that local input. Record the read time, project and card IDs, revisions and readable bodies so the reviewer can compare them with the exact-head entry and the PR's acceptance. Carry only relevant cards and preserve their access boundaries. Keep private evidence out of GitHub. Report material evidence gaps to the reviewer. Keep the author's private reasoning and suggested verdict out of both inputs.

Use the installed script's absolute path, a verified reviewer distinct from the PR author, and the project's existing round limit (three if unspecified; a fourth round needs the user's explicit word):

```sh
python3 <review>/scripts/review_pr.py start --pr 'owner/repo#123' \
  --runtime codex --reviewer <verified-login> \
  --max-rounds 3
```

Use `--runtime claude` for Claude or `--runtime antigravity` (with optional `--model claude|neon|<allowlisted-agy-model>`) for Antigravity (`agy`). Without `--runtime`, `start` uses `review_runtime` (and optional `review_model`) from `.ci/config.json` at the PR head, and when neither is given it falls back to `antigravity` with pinned model `gemini-4-hydrogen-high` (still honoring explicit `--model` or `.ci/config.json` `review_model`). `--executable` optionally selects a verified CLI binary, not a model. The launcher detaches its own process with disconnected stdin and local logs, then verifies lock ownership and startup state. It actually invokes the reviewer CLI; it is not a substitute notification transport for an existing author session. Draft PRs wait without model invocation until Ready.

```sh
python3 <review>/scripts/review_pr.py status --pr 'owner/repo#123'
```

Check `active`, PR identity, PID, startup log and eventual session/publication evidence before reporting the corresponding facts. A PID alone does not establish completed review. Runtime/auth/model failures retain artifacts and attempt a needs-user-attention handoff. Repeated GitHub/publication failures leave inactive recoverable state and must be reported by the delivery owner.

State defaults to `${XDG_STATE_HOME:-~/.local/state}/alex-coding/review/<PR-hash>`. Its key is canonical PR identity, independent of runtime/session. `--state-base` selects an explicit alternative; use it on every command and never change it to bypass ownership. Launch and lifetime locks prevent duplicate local workers. They are not a distributed lock: reuse established ownership and coordinate an explicit handoff before moving between hosts. `start` and `retry` preserve pending publication, session and rounds; explicit `continue` creates a fresh session with retained history. No credentials are stored.

The runner creates its own detached Git repository in the PR state directory and verifies exact head/base. Dirty, ignored or unrecognized local work is preserved. It never checks out or cleans the author's working copy. Review snapshots, patches and logs stay local for recovery; do not commit them. When the PR is verified merged or closed, the runner deletes its generated checkout and keeps the small state, patch and log files so status and rounds survive a reopen; a reopened PR fetches a fresh checkout. Author post-merge cleanup remains with Monitor.

## Author delivery

`start --author-runtime codex|claude|antigravity --author-session <existing-session> --checkout <owned-checkout> [--session-remote <endpoint>] [--codex <executable>]` attaches author delivery to this runner. A Claude Project thread, Codex worker or Antigravity session in a pool slot passes `--slot <pool-slot>` instead of `--checkout`, which refuses a pool slot (registered in the pool or locked as `worktree pool slot`) before creating any state: the runner then uses `alex-coding:project-monitor`'s ledger, which releases the pool slot after merge or closure rather than disposing of a worktree. `--takeover` rebinds an existing author delivery to a new session and checkout or slot only when the runner lock is free and the recorded runner and worker PIDs are dead; it keeps the ledger's events, rounds, findings and approved fingerprint and appends a `takeovers` record. Implement's delivery helper passes these. The author ledger is Monitor's state-delivery ledger, kept in this PR's state directory under `author/`, read with `gh_as bot`; review reads and writes keep `gh_as admin`. Each poll runs the review step and then one author poll, which delivers the complete current PR state to the author session (Codex native queue or bound endpoint, Claude bound endpoint or stdout, or Antigravity local outbox `outbox.jsonl`) and, after merge, synchronizes the default checkout and disposes of the owned checkout with Monitor's completion helper. The runner stops only when the review is finished and author delivery and cleanup are settled; a review handoff keeps author delivery running until merge or closure. Repeated review transport failures set `error` but keep author delivery alive.

Claude without a bound endpoint delivers through stdout, so the runner is not detached: `start` returns `monitor_command`, which the author session starts through its `Monitor` tool, and the runner writes its own status lines to `monitor.log` so stdout carries only deliveries. Antigravity delivers through its local outbox (`author/outbox.jsonl`) from the normal detached runner without `--session-remote`: `start`, `status`, `continue` and `retry` include `wait_command` (pointing at `antigravity_pr_monitor.py wait --runner-dir <state-directory>`) whenever the runner is active or unread outbox records remain, and disposable post-merge cleanup writes its final `merged + cleanup` record to the outbox before the runner exits. The author registration is immutable: repeating `start` with the same runtime, session and endpoint changes nothing, and a different one is refused. Author delivery cannot be added to a reviewer already running without it; such a PR keeps its standalone author Monitor, and the delivery helper selects that path. `continue` stops and replaces the whole runner; in stdout mode it returns `monitor_command` again. After repeated transport failures leave the review in `error` while author delivery keeps running, `retry` stops that verified runner and relaunches it with the saved review state and the same author delivery.

## Events and stopping

Only the named PR is queried. Events are a new head/base, new or edited feedback, a changed terminal CI result, merge and closure. Pending CI churn stays quiet. Skipped check runs, such as a merge workflow that a published review triggers and then skips, are not check results: they produce no CI event, and a PR whose only checks are skipped reports no checks. Automated bot feedback remains in history for evidence but does not trigger the reviewer; it still reaches the author. The fixed reviewer's robot-marked comments are self echoes; unmarked human input from that account remains visible. Dismissal is an event. Idle polling never invokes a model. There is no 30-minute model heartbeat.

The result is persisted before publication. Before every write, verify the current Ready head/base, actual admin login and repository push permission. Formal reviews and inline findings carry the runtime marker. Inline locations are checked against the reviewed patch; an invalid or unavailable location moves the complete finding into the review body without changing the verdict. A head change during review supersedes publication and leaves the new head pending; completed review attempts still count against the PR budget.

Approval and waiting-ci retain the same reviewer. A waiting-ci outcome on a snapshot with no reported checks is recorded and published as approved, so a repository without CI does not wait for results that never arrive; checks that appear later still produce terminal CI events, and merge still requires the current checks to be passing or absent. In a CI project (`.ci/config.json` at the head) `ios-plan` and `ios-unit` must both succeed on the current head; until they do, the runner stays waiting-ci, and once they pass it merges the approved head itself. Approval on an earlier head never merges a new head: the new head is assessed again first and consumes a round, including a head that only fixes CI; only an unchanged own diff after a base merge reuses the approval without a round. A new head/base assessment and reassessment of unresolved code findings consume a code-review round. CI results on a published passing review are recorded without a model call, publication or another code round; new human feedback remains review work. Pending reruns do not erase handled terminal-check events or trigger another assessment; newly observed terminal results remain actionable. A head with requested changes is not reassessed on CI results; the runner records them and waits for a new head or new feedback. Blockers at the limit, or new review work beyond it, produce needs-user-attention. Only explicit human continuation extends the budget; restarting or switching runtime cannot reset it.

A new head after a passing review whose own diff is unchanged carries the approval forward. When the review passes, the runner records the fingerprint of `git diff --binary <base>...<head>` (hashed with `git hash-object`, the algorithm the shared pre-push hook uses) in its state and checkpoint. If a later head has the same fingerprint and brings no unseen feedback, the runner publishes `APPROVE` on that head with a body stating the own diff is unchanged since the approved commit, without a model call and without consuming a round, even at the round limit. A base-only move with the same fingerprint records the new base without publication; check results on it still follow the normal CI path. A changed fingerprint, such as a merge whose conflict resolution touches the PR's files, gets a normal review; requested changes clear the recorded fingerprint.

Any terminal CI-only transition on an unchanged head/base with a published passing code review is recorded without another model call or duplicate review. CI and automatic merge failures reach the author. New human feedback, changed head/base and unresolved code findings still use the independent reviewer. This changes notification/execution cost, not the checks or their required outcomes. Continuations receive new feedback and an incremental patch when the base is unchanged; full acceptance, base-to-head patch and history stay accessible for independent inspection and recovery.

Every review contains a concise progress record and versioned checkpoint binding PR, identities, revisions and rounds. Settle the event only after required publication is confirmed, unless an explicit fresh review supersedes it as described below. Retry pending publication using its saved result and token; reuse confirmed earlier writes. GitHub and local files are not atomic, so reconcile uncertain writes from PR history before retry. Later feedback stays pending.

Verified merge or closure stops without a model call. When a restarted runner finds an interrupted invocation, it waits for a still-running worker until its recorded deadline and then stops it, adopts a validated result the worker already saved, and otherwise reruns that same head once without consuming another round; a second interruption becomes a recoverable handoff. Transient transport failures retry without model calls; three consecutive failures stop with pending results retained. `retry` reconciles that exact state without granting extra rounds or bypassing a published attention gate:

```sh
python3 <review>/scripts/review_pr.py retry --pr 'owner/repo#123'
```

`run --once` is not a read-only probe: it can execute a review or publish a pending result.

## Continue after user intervention

When the user approves a new review, Implement or Setup can request it directly. Read the PR, available prior findings and the user decision, and put that decision verbatim in a local file. A missing handoff or failed publication is not a prerequisite. Do not treat PR prose as user authorization. On a new host, establish prior ownership and progress before continuing.

```sh
python3 <review>/scripts/review_pr.py continue --pr 'owner/repo#123' \
  --decision-file <user-decision-file> --additional-rounds 1
```

Requires an explicit user decision and an open PR, independent of the old phase or pending result. The runner verifies and stops its active process before replacement, archives the previous state and unpublished findings, and starts a new model session against the current PR. The new reviewer receives the archive and current GitHub history as evidence; no old verdict is automatically published or reused as the new result. Unverifiable process ownership or a still-running orphan worker is preserved rather than starting a competing reviewer.

Total rounds are retained. One additional round is the default; use `--additional-rounds 0` when the existing budget is sufficient. Larger extensions require existing user/project authorization. `--runtime`, `--complexity` and `--model` can explicitly change here, and `--acceptance-file` replaces the saved acceptance input. This request does not require `retry` to succeed first, a synthetic commit, manual state edits or author approval. Closed/merged PRs cannot continue; reopened PRs can. Without a fresh-review decision, use `retry` for the saved result.

## Legacy repository watchers

`codex_repo_monitor.py`, `claude_repo_monitor.py` and `repo_monitor_core.py` remain available to finish existing watches/claims. The new entrypoint never starts them or scans the repository. Keep their original script cache available while listeners or delivered batches use it.

Before migration, stop the exact legacy listener through its runtime, reconcile delivered/claimed batches using the original acknowledgements, and preserve the state. Record prior review-loop progress in an authorized reviewer handoff before starting the new worker; missing new-format metadata does not mean zero rounds. When prior reviews lack a checkpoint, startup requires `--completed-rounds` with the verified cumulative count; an existing checkpoint always takes precedence. If that progress cannot be established, report the migration gap rather than resetting it. Never launch both owners for the PR or silently edit a queued notification.

Legacy procedures: [Codex](monitor.md), [Claude](claude-monitor.md), [batch publication](review-batches.md). These are migration references, not default launch paths. Author Monitor owns its separate delivery and protected completion contract; follow its selected runtime rather than applying reviewer acknowledgements to author notifications.
