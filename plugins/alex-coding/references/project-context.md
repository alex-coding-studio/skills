# Repository Entry and Declared Context

Start in the target repository and read its root `AGENTS.md` before planning, setup, implementation, review, or investigation. Follow applicable workspace rules and the context provider and engineering sources declared by the repository. If there is no root entry, use the applicable repository instructions, README and relevant project documents. An explicitly declared legacy source such as `ProjectContext.md` remains valid. Preserve authored files and separate approval requirements for protected instructions or context changes.

Read only what the task needs: current decisions, architecture, constraints, pitfalls, unresolved questions, the task card and its referenced decisions, and actual verification and delivery rules. Source, manifests, tests, commands, Git and CI supply observed engineering facts. Reuse applicable reads within the same work and refresh them when the scope, revision, handoff or evidence changes. Report any material gap or conflict and continue where current verified evidence suffices.

## When the workspace declares Semina

Use the shared workspace route and the declared `projectId` directly on local or remote MCP, including in linked worktrees. For an overview or a discussion, call `semina_read_project`; read modules and cards only when the topic needs them, paginating when needed. Small direct fixes need no card reads. For task-card work, call `semina_read_task`, then read the decision cards it references and, when needed, its module and relevant pitfalls. Use the project view if the task has no module or needs broader context. Read relevant pending questions without treating them as decided. If a required ID is missing, resolve it by explicit project identity only when needed. Repositories without a Semina declaration use their own sources and need no registration.

Follow the workspace's writeback rules when authorized. Plan writes settled decisions, superseded markers and task cards as the user settles them, with links. Small direct fixes record only a reusable pitfall or a changed decision. Task-card work records approved direction changes on the task card when approved, and after reviewer approval and before merge aligns the referenced decision cards and the module card with the final diff. Unresolved questions stay pending. Read existing cards with their current revisions before updates and reread on conflicts. Only the task owner or an authorized Agent completes a task, after its last PR merges, with `knowledgeImpact` in the same call using `{cardIds: [...]}` for cards created or updated by the task or `{none: "one-line reason"}`. Review-only work carries no write obligation. Project context supplies evidence and constraints within the accepted scope. Keep durable project knowledge in the declared provider, not in local Agent memory.

Keep reproducible engineering facts in versioned repository sources. For other declared providers, follow the repository's own read, update and approval rules.
